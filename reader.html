EasyTutor Exam Feature Documentation

1. Overview

The Exam Feature lets users—students, teachers, and institutes—take mock exams in EasyTutor. There are two types:

  • Trial Exam: Free, one-time use per user.
  • Paid Exam: Bought directly with real money via Razorpay, allows multiple attempts.

Exams are purchased using Razorpay (cards, UPI, etc.), not coins. Coins, managed through wallets and wallet_transactions, are only for viewing profiles (e.g., student viewing a teacher’s details or institute viewing a student’s profile) and are not part of this feature. Admins create exams, set questions, timers, prices, and choose which user types (students, teachers, institutes) can take each exam. After an exam, users see their score, correct/wrong answers, and can retake paid exams. The app saves progress if it crashes or loses internet, and answers stay hidden during the exam to prevent cheating.

2. Database Tables Needed

Here’s a list of tables we need, what changes we’re making to existing ones, and what’s new. The wallet_transactions table will handle Razorpay payments for exams, while coins (via wallets and wallet_transactions) are only for profile viewing.

Existing Tables (with Changes)

  1. exams (Stores exam details):

    • What’s there: ID, name, subject, status (active/inactive), created/updated timestamps.
    • Changes:
      • Add timer_duration (minutes, e.g., 60 for a 1-hour exam).
      • Add negative_marking_enabled (yes/no, to turn on negative marking).
      • Add negative_marking_threshold (number of wrong answers for a penalty, e.g., 3).
      • Add negative_marking_value (penalty amount, e.g., -1 point).
      • Add target_users (list of allowed users, e.g., [“student”, “teacher”, “institute”]).
      • Add price (amount in rupees for paid exams, e.g., 199.00).
    • Why: Timer and negative marking fields simplify scoring. Target users filter exams by role. Price is for Razorpay payments, replacing coin-based plans.

  2. questions (Stores exam questions):

    • What’s there: ID, question text, options (A, B, C, D), correct answer, exam ID, created/updated timestamps.
    • Changes:
      • Add marks (points per question, e.g., 1 or 2).
    • Why: Marks allow flexible scoring, like making some questions worth more points.

  3. student_exams (Tracks purchased exams):

    • What’s there: ID, student ID, exam ID, plan ID, transaction ID, status, purchased timestamp.
    • Changes:
      • Rename to user_exams (to support all user types: students, teachers, institutes).
      • Replace student_id with user_id (to work for all roles).
      • Remove plan_id (no coins/plans for exams, since we’re using Razorpay).
      • Update status to “PURCHASED”, “STARTED”, “COMPLETED” (to track exam progress).
      • Add is_trial (yes/no, to mark trial exams).
      • Keep transaction_id (links to wallet_transactions for Razorpay payments).
    • Why: Supports all users, tracks trial exams, and connects to Razorpay payments via wallet_transactions.

  4. wallet_transactions (Tracks Razorpay payments for exams and coin transactions for profile viewing):

    • What’s there: ID, wallet ID, user ID, units (coins), amount (rupees), type (CREDIT/DEBIT), purpose (e.g., EXAM_PURCHASE, VIEW_PROFILE), plan ID, payment ID (Razorpay), order ID (Razorpay), reference ID, status (PENDING/COMPLETED/FAILED), description, created timestamp.
    • Changes:
      • Add exam_id (links to the exam purchased via Razorpay).
      • Add “TRIAL_ACTIVATION” to purpose options (for free trial exams).
    • Why: Reuses the table for Razorpay payments (EXAM_PURCHASE) and trial activations (TRIAL_ACTIVATION) without coins. units is ignored for exams but used for profile viewing.

  5. plans (Holds coin plans for profile viewing):

    • What’s there: ID, name, amount (rupees), units (coins), exam ID (unused), description, type (RECHARGE/EXAM), active status, timestamps.
    • Changes: None.
    • Why: Only used for buying coins for profile viewing, not exams.

New Table

  1. exam_attempts (Tracks each exam attempt):
    • Columns:
      • ID (unique ID for the attempt).
      • user_exam_id (links to user_exams).
      • start_time (when the attempt started).
      • end_time (when it finished).
      • remaining_time (seconds left, to resume after crashes).
      • answers (list of question IDs and user’s chosen options, e.g., { “q1”: “A”, “q2”: “C” }).
      • score (percentage, e.g., 85.5).
      • correct_count (number of correct answers).
      • wrong_count (number of wrong answers).
      • attempted_count (number of questions answered).
      • Created/updated timestamps.
    • Why: Saves each attempt’s answers, score, and progress for later review.

3. Admin Routes (APIs for Admins)

These APIs let admins manage exams. Each route lists the tables it affects. They help admins set up exams, questions, and prices.

  1. Create Exam (POST /admin/exams):

    • What it does: Creates a new exam with a name, subject, timer, price, negative marking settings, and target users (students, teachers, institutes).
    • Tables:
      • exams (adds the new exam).
    • Details: Admin sets “Math Test” for students, priced at ₹199, with a 60-minute timer and negative marking (3 wrong answers = -1 point). For trials, price is ₹0.

  2. Update Exam (PUT /admin/exams/:examId):

    • What it does: Updates an exam’s details, like name, timer, price, or target users.
    • Tables:
      • exams (updates the exam).
    • Details: Admin changes “Math Test” price to ₹249 or adds “teachers” to target users.

  3. Add Questions (POST /admin/exams/:examId/questions):

    • What it does: Adds questions to an exam, including text, four options, correct answer, and marks.
    • Tables:
      • questions (adds new questions).
    • Details: Admin adds 50 questions to “Math Test,” each worth 1 mark.

4. User Routes (APIs for Users)

These APIs let users (students, teachers, institutes) find, buy, take, and review exams. Each route lists the tables it uses. They focus on Razorpay for payments, using wallet_transactions.

  1. List Available Exams (GET /exams/list):

    • What it does: Shows exams the user can take, based on their role (student, teacher, institute). Includes trial exams (free) and paid exams (with price), plus whether they’ve bought or tried them.
    • Tables:
      • exams (get exam details like name, price, target users).
      • user_exams (check if the user bought the exam).
      • exam_attempts (check if a trial was attempted).
    • Details: A student sees “Math Test” (₹199, not bought) and “Science Trial” (free, not attempted).

  2. Purchase Exam (POST /exams/:examId/purchase):

    • What it does: Lets a user buy a paid exam via Razorpay.
    • Tables:
      • wallet_transactions (record the Razorpay payment with purpose = EXAM_PURCHASE).
      • user_exams (add the exam to the user’s list).
      • exams (get exam price).
    • Details: Student pays ₹199 for “Math Test” using Razorpay. The payment is saved in wallet_transactions (with units = 0 since no coins), and the exam is unlocked.

  3. Activate Trial Exam (POST /exams/:examId/trial/activate):

    • What it does: Starts a free trial exam (one-time per user).
    • Tables:
      • user_exams (add the trial exam).
      • wallet_transactions (record with purpose = TRIAL_ACTIVATION, amount = 0, units = 0).
      • exam_attempts (check if the trial was already taken).
      • exams (verify it’s a trial exam with price = 0).
    • Details: Student starts “Science Trial” for free, recorded in wallet_transactions as a zero-cost transaction.

  4. Start Exam (POST /exams/:examId/start):

    • What it does: Begins an exam, starts the timer, and shows questions.
    • Tables:
      • exam_attempts (create a new attempt).
      • questions (get questions, without answers).
      • exams (get timer duration).
      • user_exams (confirm the user has access).
    • Details: Student starts “Math Test” and sees the first question with a 60-minute timer.

  5. Submit Exam (POST /exams/:examId/submit):

    • What it does: Submits the user’s answers, calculates the score, and saves the results.
    • Tables:
      • exam_attempts (save answers, score, correct/wrong counts).
      • questions (check correct answers).
      • exams (apply negative marking rules).
    • Details: Student submits “Math Test,” gets 85%, with 3 points deducted for wrong answers.

  6. List Exam Attempts (GET /exams/:examId/attempts):

    • What it does: Shows all attempts for an exam, with scores and dates.
    • Tables:
      • exam_attempts (get attempt details).
      • user_exams (confirm access).
    • Details: Student sees they scored 85% and 90% on “Math Test” attempts.

  7. View Attempt Details (GET /exams/:examId/attempts/:attemptId):

    • What it does: Shows detailed results, including which questions were correct or wrong.
    • Tables:
      • exam_attempts (get answers and score).
      • questions (get question text and correct answers).
    • Details: Student reviews “Math Test” and sees they picked “B” for question 1, but “A” was correct.

  8. List Payments (GET /exam-payments):

    • What it does: Shows all exam purchases and trial activations with exam name, amount paid (₹0 for trials), and date.
    • Tables:
      • wallet_transactions (get payment details with purpose = EXAM_PURCHASE or TRIAL_ACTIVATION).
      • exams (get exam names).
    • Details: Student sees they paid ₹199 for “Math Test” and activated “Science Trial” for ₹0 on May 1, 2025.

7. Target Users Option

When admins create or edit an exam, they choose which user types can take it: students, teachers, institutes, or any combination. This is saved in the exams.target_users field as a list (e.g., ["student", "teacher"]).

  • How it works:
    • In the Create/Edit Exam Screen, admins see checkboxes: “Students,” “Teachers,” “Institutes.” They check one or more to set who can access the exam.
    • The List Available Exams API checks the user’s role (from their login) against target_users. For example, a teacher only sees exams where target_users includes “teacher.”
    • This applies to both trial and paid exams—role filtering happens first.
  • Details:
    • Admins can limit an exam to one role (e.g., students) or allow multiple (e.g., students and teachers).
    • If no roles are selected, the exam is hidden from all users until the admin fixes it.
    • The app shows a friendly message if no exams match the user’s role (e.g., “No exams available for institutes yet”).
  • Example: Admin creates “Math Test” for students only. A student sees it in their Exam Home Screen, but a teacher doesn’t.

8. Scoring and Negative Marking

Here’s how scores are calculated, in simple terms:

  • Basic Score: Count correct answers, divide by total questions, multiply by 100. Example: 42 correct out of 50 questions = (42/50) * 100 = 84%.
  • Marks: Each question has a mark value (e.g., 1 or 2). If questions have different marks, the score is (total marks for correct answers) / (total possible marks) * 100. Example: 40 marks correct out of 50 total marks = (40/50) * 100 = 80%.
  • Negative Marking: If turned on in the exams table:
    • Check negative_marking_enabled (yes/no).
    • If yes, count wrong answers. For every negative_marking_threshold wrong answers (e.g., 3), subtract negative_marking_value (e.g., -1).
    • Example: 42 correct, 9 wrong, threshold = 3, penalty = -1. Penalty = floor(9/3) * -1 = -3. Final score = 84 - 3 = 81%.
  • Minimum Score: Score can’t go below 0%, even with big penalties.
  • Details:
    • Negative marking is set per exam by admins in the Create/Edit Exam Screen.
    • Users see the penalty in their results (e.g., “-3 points for 9 wrong answers”).
    • If negative marking is off, only correct answers count toward the score.

9. Edge Cases (What Could Go Wrong and How We Fix It)

Here’s how we handle tricky situations to keep the app smooth, fair, and user-friendly:

  1. App Crashes or Closes:

    • Problem: User’s phone battery dies or they accidentally close the app during an exam.
    • Fix: Save answers and remaining time locally on the phone every 5 seconds. When they reopen, the app loads the saved data and syncs with the server to resume exactly where they left off. The timer runs server-side to prevent cheating.
    • Details: If the timer expires while the app is closed, the exam auto-submits with the saved answers. Users see a “Resuming your exam” message.

  2. Internet Drops:

    • Problem: User loses Wi-Fi or data mid-exam.
    • Fix: Store answers locally and show a “No Internet, saving locally” message. Users can keep answering. When internet returns, answers sync to the server. If the timer runs out, the app submits saved answers.
    • Details: Submission requires internet, but answering works offline. Users get a “Reconnected, syncing” message when back online.

  3. Cheating (Seeing Answers):

    • Problem: User tries to peek at correct answers using browser tools or app inspection.
    • Fix: Questions are sent to the app without answers during the exam. Correct answers are only sent after submission or when viewing results.
    • Details: Answers are stored securely on the server. Even if a user inspects the app, they can’t see correct answers until the exam is done.

  4. Trial Exam Abuse:

    • Problem: User tries to take a trial exam more than once.
    • Fix: Before allowing a trial, check user_exams and exam_attempts for the user and exam. If they’ve already taken it, block them with a message: “You’ve already taken this trial.”
    • Details: Trials are tied to the user’s ID, ensuring one attempt per exam per user.

  5. Payment Fails:

    • Problem: Razorpay payment fails (e.g., card declined or UPI error).
    • Fix: Mark the payment as “FAILED” in wallet_transactions. Show a clear error: “Payment failed, please try again.” User can retry without being double-charged.
    • Details: Only “COMPLETED” payments in wallet_transactions unlock the exam. Failed attempts are logged for troubleshooting.

  6. Wrong Role Access:

    • Problem: A teacher tries to access a student-only exam.
    • Fix: The List Available Exams API filters exams by target_users. If the user’s role (e.g., teacher) isn’t in the list, the exam doesn’t appear.
    • Details: Users see a message like “No exams available for your role” if none match. This check happens server-side to prevent tampering.

  7. Timer Issues:

    • Problem: User tries to pause the timer or cheat by changing their phone’s clock.
    • Fix: The timer runs server-side, using start_time and remaining_time in exam_attempts. The app syncs with the server every 30 seconds to stay accurate, ignoring the phone’s clock.
    • Details: If a user tries to manipulate the timer, the server’s time overrides it. Users see a warning if they try to pause: “Timer cannot be paused.”

  8. Double Payments:

    • Problem: User accidentally pays twice for the same exam.
    • Fix: Before processing a payment, check user_exams to see if the user already owns the exam. If they do, block the purchase and show: “You already own this exam.”
    • Details: Razorpay’s order_id ensures payments aren’t duplicated. Refunds can be issued via Razorpay if needed.

10. Putting It All Together

Here’s the big picture of how the Exam Feature works:

  • For Users:
    • Browse exams that match your role (student, teacher, institute).
    • Take a free trial exam once or buy a paid exam with Razorpay (cards/UPI).
    • Answer questions within the timer, with progress saved if the app crashes or internet drops.
    • Review your score, see correct/wrong answers, and retake paid exams as needed.
    • Check your payment history to track purchases and trial activations.
  • For Admins:
    • Create exams with custom names, timers, prices, and target users.
    • Add questions and set negative marking rules (optional).
    • Update exams anytime to change prices, target users, or other details.
  • Razorpay Payments:
    • Users pay directly with cards or UPI, no coins involved.
    • Payments are secure, verified, and tracked in wallet_transactions with EXAM_PURCHASE or TRIAL_ACTIVATION.
    • Trials are free and logged as zero-cost transactions.
  • Fair and Safe:
    • Answers stay hidden during exams to prevent cheating.
    • Progress is saved during crashes or internet issues.
    • Trials are limited to one per user, and role-based access is enforced.
